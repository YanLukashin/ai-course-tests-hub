## Вопрос 1

**Тип:** Сопоставление (4 пары)
**Урок:** 7.1 — Что такое vibe coding и зачем это предпринимателю
**Цель:** З-7.1 · Сложность: лёгкий

**Текст:** Соедините каждое описание с подходом к созданию приложений.

**Описания (слева):**
1. Пользоваться может кто угодно. Код пишет ИИ, человек его не читает и не проверяет. Код принадлежит вам — можно забрать и перенести куда угодно.
2. Код пишет ИИ, но разработчик проверяет каждую строку, тестирует и понимает, что внутри.
3. Приложение собирается мышкой из готовых блоков. Кода вы не видите вообще — он скрыт за платформой, и перенести решение в другое место без переделки нельзя.
4. Визуальный конструктор плюс возможность при необходимости залезть в код. Для бизнес-пользователей, которые немного разбираются в технике.

**Подходы (справа):**
- A) No-code
- B) Low-code
- C) Vibe coding
- D) AI-assisted coding (ИИ-помощник)

**Правильный ответ:**

| Описание | Подход |
|----------|--------|
| 1 | C |
| 2 | D |
| 3 | A |
| 4 | B |

**Пояснение:** Подходы различаются по трём параметрам: кто пользователь, проверяется ли код человеком и насколько вы привязаны к платформе. Главные границы — vibe coding отличается от ИИ-помощника тем, что вы код не проверяете, а от no-code тем, что владеете кодом и не зависите от платформы.

**Почему путают:** Чаще всего описание 2 (код проверяется) ошибочно относят к vibe coding — но проверка кода как раз и есть граница между ними.

**Зачёт:** минимум 3 из 4 пар. Полный балл: 4 из 4.

## Вопрос 2

**Тип:** Множественный выбор (1 правильный)
**Урок:** 7.1 — Что такое vibe coding и зачем это предпринимателю
**Цель:** З-7.1 · Сложность: лёгкий

**Текст:** Предприниматель описал ИИ обычными словами, какое приложение хочет. ИИ сгенерировал код, предприниматель принял все правки не глядя, сам код ни разу не открывал — проверил только одно: работает приложение или нет. Какой это подход?

- A. Vibe coding ✅
- B. AI-assisted coding
- C. No-code
- D. Low-code

**Правильный ответ:** A — Vibe coding

**Пояснение:** Определяющий признак vibe coding — осознанный отказ читать и проверять код. Вы делегируете написание полностью и оцениваете только результат: работает или нет. Именно это в описании и происходит.

**Почему остальные неверны:** B — там человек проверяет каждую строку; C и D — там приложение собирается в конструкторе, а здесь человек описывает задачу словами и получает код.

## Вопрос 3

**Тип:** Сопоставление (6 пар)
**Урок:** 7.2 — Минимум теории: 6 концепций для разговора с ИИ
**Цель:** З-7.2 · Сложность: лёгкий

**Текст:** Соедините ситуацию из реальной работы с прототипом с технической концепцией, которая за ней стоит.

**Ситуации:**
1. Приложение работает на моём компьютере, но коллеги не могут открыть его по ссылке.
2. Данные из формы пропадают после перезагрузки страницы — нигде не сохраняются.
3. Нужно, чтобы панель с цифрами компании видели только менеджеры, а не любой человек по ссылке.
4. Хочу поменять то, что видит клиент: цвет кнопки, расположение полей, текст на странице.
5. Нужно подключить приложение к Telegram, чтобы оно отправляло уведомления.
6. Расчёт скидки по сложным правилам и проверка промокода — это процессы «на кухне», не то, что видит клиент.

**Концепции (справа):**
- A) Фронтенд
- B) Бэкенд
- C) API
- D) База данных
- E) Деплой
- F) Аутентификация

**Правильный ответ:**

| Ситуация | Концепция |
|----------|-----------|
| 1 | E |
| 2 | D |
| 3 | F |
| 4 | A |
| 5 | C |
| 6 | B |

**Пояснение:** Эти 6 слов нужны не для программирования, а чтобы корректно ставить задачу ИИ. Фронтенд — витрина (что видит клиент), бэкенд — кухня (процессы за кулисами), API — официант (связь с другими сервисами), база данных — где хранятся данные между визитами, деплой — публикация по ссылке, аутентификация — замок на двери.

**Почему путают:** ситуации 2 и 6 легко перепутать — но «данные пропадают» это про хранение (база данных), а «сложный расчёт за кулисами» это про логику (бэкенд).

**Зачёт:** минимум 5 из 6 пар. Полный балл: 6 из 6.

## Вопрос 4

**Тип:** Множественный выбор (1 правильный)
**Урок:** 7.2 — Минимум теории: 6 концепций для разговора с ИИ
**Цель:** З-7.2 · Сложность: лёгкий

**Текст:** Предприниматель просит ИИ: «Сделай так, чтобы заявки клиентов сохранялись навсегда». ИИ не до конца понимает, что имеется в виду. Какую техническую концепцию предпринимателю нужно знать, чтобы переформулировать запрос точнее?

- A. Фронтенд
- B. Бэкенд
- C. База данных ✅
- D. Деплой

**Правильный ответ:** C — База данных

**Пояснение:** «Сохранять навсегда» означает, что данные должны где-то лежать и быть доступны при следующем визите — это и есть база данных. Зная это слово, предприниматель сформулирует запрос так, чтобы ИИ добавил хранилище, а не просто показал данные на экране.

**Почему остальные неверны:** Фронтенд — только внешний вид; деплой — публикация приложения по ссылке; бэкенд — общая логика за кулисами, но за хранение отвечает именно база данных.

## Вопрос 5

**Тип:** Множественный выбор (несколько правильных из 6)
**Урок:** 7.1 / 7.6 — зона применимости vibe coding
**Цель:** П-7.1 · Сложность: средний

**Текст:** Отметьте все задачи, которые **хорошо подходят** для vibe coding.

- A. Лендинг для разового мероприятия ✅
- B. Персональный трекер привычек ✅
- C. Калькулятор стоимости услуг ✅
- D. Система онлайн-оплаты
- E. Приложение для хранения медицинских записей пациентов
- F. Корпоративная ERP-система

**Правильный ответ:** A, B, C

**Пояснение:** Зелёная зона vibe coding — лендинги, персональные инструменты («software for one»), калькуляторы, дашборды, MVP для проверки гипотез. Это задачи без чувствительных данных и без высокой цены ошибки.

**Почему остальные неверны:** D — платежи требуют аудита безопасности; E — медицинские данные это персональные данные под 152-ФЗ; F — корпоративная система это высокая нагрузка и сложная логика. Всё это красная зона.

**Зачёт:** минимум 2 правильных и ни одного неправильного. Полный балл: все 3 правильных без ошибок.

## Вопрос 6

**Тип:** Кейс + множественный выбор (несколько правильных из 5)
**Урок:** 7.6 — Типичные ошибки и границы подхода
**Цель:** П-7.1 · Сложность: средний

**Текст:** Предприниматель собрал вайб-кодингом внутренний инструмент для своей команды. Он хорошо работает уже несколько месяцев. Теперь предприниматель хочет открыть его для клиентов: добавить ввод персональных данных (имя, телефон, email) и подключить онлайн-оплату — всё тем же способом, без разработчика. Какие реальные риски при этом возникают?

- A. Уязвимости в ИИ-коде, который никто не проверял на безопасность ✅
- B. Нарушение требований к обработке персональных данных (152-ФЗ) ✅
- C. Если что-то сломается, чинить будет некому — код невозможно поддерживать ✅
- D. Приложение будет работать медленно, потому что ИИ-код неоптимизирован
- E. Клиенты не будут доверять приложению, если узнают, что оно создано ИИ

**Правильный ответ:** A, B, C

**Пояснение:** При переходе из «внутреннего инструмента» в production с чужими данными и деньгами включаются три настоящих риска: безопасность (по исследованиям, 25–70% ИИ-кода содержит уязвимости), требования к персональным данным и технический долг — код, который никто не сможет починить.

**Почему остальные неверны:** D — скорость не главная проблема на малом масштабе; E — это про восприятие, а не про техническую безопасность, и не относится к рискам перехода в production.

**Зачёт:** минимум 2 правильных без дистракторов. Полный балл: все 3 правильных, ни одного дистрактора.

Клиенты оставляют имя, телефон и описание задачи. Периодически при редактировании одной заявки пропадают данные другой. Теперь владелец хочет добавить интеграцию с 1С. Какие сигналы указывают, что прототип пора передавать профессиональному разработчику?

## Вопрос 8

**Тип:** Множественный выбор (несколько правильных из 5)
**Урок:** 7.6 — Типичные ошибки и границы подхода
**Цель:** П-7.2 · Сложность: средний

**Текст:** Вы решили передать свой vibe-coded прототип профессиональному разработчику. Что должно входить в «пакет передачи»?

- A. Аудит кода на уязвимости ✅
- B. Ревизия модели данных ✅
- C. Проверка безопасности и тесты ✅
- D. Полное переписывание приложения с нуля
- E. Подробная документация каждой строки кода

**Правильный ответ:** A, B, C

**Пояснение:** Передать прототип — это не «вот ссылка, разберись». Формат передачи превращает непонятный код в то, с чем профессионал может работать: проверить на уязвимости, разобраться с тем, как устроены данные, и протестировать.

**Почему остальные неверны:** D — переписывать с нуля нужно не всегда, это зависит от ситуации; E — построчная документация для vibe-coded приложения нереалистична и не входит в стандартную передачу.

**Зачёт:** минимум 2 правильных без дистракторов.

## Вопрос 9

**Тип:** Кейс + выбор лучшего решения (1 правильный из 4)
**Урок:** 7.3 — Промптинг для кода
**Цель:** П-7.1 (через призму Пр-7.1) · Сложность: средний

**Текст:** Вы хотите создать форму обратной связи для клиентов с полями имя, email и текст сообщения. Какой промпт для ИИ-генератора кода лучший?

- A. «Используй React и Tailwind, создай компонент с useState для формы и валидацией email через regex.»
- B. «Создай форму обратной связи для клиентов: поля имя, email и текст сообщения. Email должен проверяться на корректность. Дизайн минималистичный, спокойные цвета, интерфейс на русском, обязательно мобильная версия.» ✅
- C. «Сделай форму.»
- D. «Сделай форму обратной связи, и заодно личный кабинет, систему оплаты и рассылку писем клиентам.»

**Правильный ответ:** B

**Пояснение:** Главное правило промптинга для кода — описывать результат, а не реализацию. Вариант B говорит, что должно получиться и в каких рамках (что увидит клиент, какие ограничения), не требуя технических знаний.

**Почему остальные неверны:** A — заставляет вас разбираться в технологиях, это не ваша зона; C — слишком расплывчато, ИИ всё додумает сам; D — нарушает правило «одна функция — один промпт», пытаясь сделать всё одним запросом.

## Вопрос 10

**Тип:** Кейс + сопоставление (5 ограничений → 2 категории)
**Урок:** 7.6 / 7.7 — границы подхода и чек-лист ограничений
**Цель:** А-7.1 · Сложность: сложный

**Текст:** Предприниматель собрал вайб-кодингом лендинг записи для своей студии услуг. Лендинг принимает заявки с именем, телефоном и email клиента, а также собирает предоплату через форму оплаты. Он задеплоен и уже доступен по ссылке. Распределите каждое ограничение по категориям: **критичное** (блокирует запуск в production) или **допустимое** (можно показывать клиентам/коллегам как есть).

**Ограничения:**
1. Нет входа по паролю, хотя приложение хранит персональные данные клиентов
2. Не проверены граничные случаи для формы оплаты
3. Ключи доступа вписаны прямо в код
4. Дизайн неидеально смотрится на телефоне
5. Не все надписи на странице переведены на русский

**Правильный ответ:**

| Ограничение | Категория |
|-------------|-----------|
| 1 | Критичное |
| 2 | Критичное |
| 3 | Критичное |
| 4 | Допустимое |
| 5 | Допустимое |

**Пояснение:** Граница простая: критично то, что взрывается при росте и угрожает данным или деньгам клиентов — отсутствие защиты на персональных данных, непроверенная оплата, открытые ключи доступа. Допустимо то, что некрасиво, но не опасно для текущего показа — вид на телефоне и недопереведённые надписи.

**Почему важно различать:** Умение отделить «стоп-кран» от «косметики» — это и есть зрелый взгляд на свой прототип. Путаница приводит либо к запуску небезопасного продукта, либо к бесконечной полировке мелочей вместо запуска.

**Зачёт:** минимум 4 из 5 распределены верно. Полный балл: 5 из 5.
